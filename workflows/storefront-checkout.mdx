A shopper goes from browsing to a paid order. Steps 1–6 run with the publishable client in the
browser (catalog, cart, shipping, an optional stock reservation); the order and payment in steps 7–8
run with the secret client on your server. Step 7 builds the same order three ways — base, with a
promotion, with a promotion and a gift card — alongside the two rejections that guard the totals.
[Workflow Examples](/workflows/introduction) has the client setup.

## 1. Browsing the catalog

A plain list, then the narrowing and trimming a real grid does.

```typescript
const { products } = await storefront.products.listProducts({ limit: 20 });
```

```json Response
{
  "products": [
    {
      "id": "0186665f-f0a1-4c79-976a-919b5b1c2daa",
      "name": "Samsung Galaxy Watch 6",
      "slug": "samsung-galaxy-watch-6-0186",
      "price": 299,
      "sale_price": null,
      "currency": "USD",
      "primary_media_url": "https://images.unsplash.com/photo-1523275335684-37898b6baf30?w=400",
      "variants": [
        { "variant_id": "e98631a9-7852-4fe8-8efe-988935d5922a", "sku": "SAM-WATCH-6-44-0186", "price": 299, "stock": 150 }
      ]
    }
  ],
  "pagination": { "limit": 20, "next_cursor": "MjAyNi0wNi0xOVQyMDow...", "has_more": true }
}
```

A grid needs a few columns, not the full product. `fields` fetches only those, keeping the response
small:

```typescript
const { products } = await storefront.products.listProducts({
  limit: 20,
  fields: 'id,name,price,sale_price,media',
});
// Each product now carries only those keys. Conversely, full: true returns the
// complete object (media, specifications, every variant) for a product detail page.
```

<Note>
  `fields` accepts a fixed allowlist of column names (e.g. `id`, `name`, `price`, `sale_price`,
  `media`, `thumbnail_url`, `category_name`, `stock`) — **not** arbitrary keys. An unknown name
  returns `400 invalid_request` ("Invalid field names: …"). `id` and `product_id` are
  interchangeable.
</Note>

Lists are [cursor-paged](/sdk/introduction#cursor-based-pagination): `next_cursor` goes back as
`cursor` until `has_more` is false.

```typescript
let cursor: string | undefined;
do {
  const page = await storefront.products.listProducts({ limit: 50, cursor });
  // …render page.products…
  cursor = page.pagination.has_more ? page.pagination.next_cursor : undefined;
} while (cursor);
```

A category page filters on `categoryId`, and combines with `subcategoryId` for hierarchy:

```typescript
const { products } = await storefront.products.listProducts({
  categoryId: '…category-uuid…',
  limit: 20,
});
```

<Tip>
  Build navigation with `storefront.taxonomy.listCategories()`, or wire a search box with
  `storefront.search.searchProducts({ q: 'wireless headphones' })`. All read-only, all
  publishable-key — see [Search & discovery](/workflows/search-and-discovery).
</Tip>

## 2. Adding to an anonymous cart

A shopper who isn't signed in gets a **session cart** keyed by an `X-Session-Id` you generate and
persist (a UUID in a cookie). No customer token needed yet.

```typescript
const sessionId = crypto.randomUUID(); // generate once, store in a cookie

const cart = await storefront.cartWishlist.addToCart({
  xSessionId: sessionId,
  requestBody: { variant_id: 'e98631a9-7852-4fe8-8efe-988935d5922a', quantity: 2 },
});
```

```json Response
{
  "items": [
    {
      "id": "09695de2-73ac-45ea-b2cb-76f9751b9846",
      "product_id": "0186665f-f0a1-4c79-976a-919b5b1c2daa",
      "variant_id": "e98631a9-7852-4fe8-8efe-988935d5922a",
      "product_name": "Samsung Galaxy Watch 6",
      "product_sku": "SAM-WATCH-6-44-0186",
      "quantity": 2,
      "unit_price": 299,
      "selling_price": 299,
      "total_price": 598,
      "stock_available": 150,
      "has_variants": true
    }
  ],
  "session_id": "1f8d2c44-...",
  "customer_id": null
}
```

The line item's `id` (`09695de2-…`) is the cart-item id, not the product or variant id, and it is the
handle for updating or removing that line. It is distinct from `variant_id`: the same variant added
twice remains one line, mutated by its `id`.

## 2b. Managing the cart — view, update, remove, clear

The rest of the cart lifecycle runs on the same identity as the add: `xSessionId` for an anonymous
cart, or `xAuthToken` once the shopper signs in.

Reading the current cart, for a cart drawer or a badge count:

```typescript
const cart = await storefront.cartWishlist.getCart({ xSessionId: sessionId });
// → { items: [...], total_items: 2, subtotal: 598 }
```

Changing a line's quantity addresses the line by its cart-item `id`, not the variant:

```typescript
await storefront.cartWishlist.updateCartItem({
  id: '09695de2-73ac-45ea-b2cb-76f9751b9846', // the cart-item id from the add response
  xSessionId: sessionId,
  requestBody: { quantity: 3 },
});
```

<Note>
  `updateCartItem` with `quantity: 0` is equivalent to `removeCartItem`, so a quantity stepper
  decremented to zero needs no separate branch.
</Note>

Removing a single line explicitly, for a "✕" on the row:

```typescript
await storefront.cartWishlist.removeCartItem({
  id: '09695de2-73ac-45ea-b2cb-76f9751b9846',
  xSessionId: sessionId,
});
// → { success: true, message: 'Item removed from cart' }
```

Emptying the whole cart, for a "Clear cart" action or a reset after an abandoned checkout:

```typescript
await storefront.cartWishlist.clearCart({ xSessionId: sessionId });
// → { success: true, message: 'Cart cleared' }
```

The steps that follow assume a populated cart, so re-add an item after clearing. The wishlist mirrors
this shape — `addToWishlist` / `removeFromWishlist` / `moveWishlistToCart`, the last of which hands a
saved item back into the cart flow above.

## 3. Signing the shopper in

Checkout needs a session for the shopper. Registration and login are `sk`-only endpoints, so they run
on your server with the secret client.

```typescript
// On your server
const { customer, session } = await server.authentication.login({
  requestBody: { email: 'john.doe@example.com', password: '••••••••' },
});
// Hand session.access_token back to the browser to use as xAuthToken.
```

```json Response
{
  "message": "Login successful",
  "user": { "id": "df648f68-39b3-4ba6-9be2-ff0a9393c02b", "email": "john.doe@example.com", "email_confirmed": true },
  "customer": { "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9", "name": "John Doe", "email": "john.doe@example.com", "tier": "bronze", "total_purchases": 0 },
  "session": { "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.<redacted>.signature", "refresh_token": "5h2g7k9m1n3p...", "expires_in": 3600 }
}
```

<Tip>
  Passwordless? Use `server.authentication.sendMagicLink(...)` or the OTP pair
  (`sendMagicLink` → `verifyOtp`) — both return the same `{ user, customer, session }` envelope.
</Tip>

## 4. Merging the anonymous cart into the customer

Everything the shopper added before signing in carries onto their account.

```typescript
const merged = await storefront.cartWishlist.mergeCart({
  xAuthToken: session.access_token,
  requestBody: { session_id: sessionId, customer_id: customer.id },
});
// merged.customer_id === customer.id  → the cart now belongs to the signed-in shopper
```

## 5. Quoting shipping

Delivery is quoted for the shopper's address before the order is totalled. Read-only, publishable
key. The amount returned here is the one the order endpoint validates against, so it is the amount
the total is built from.

```typescript
const quote = await storefront.shipping.calculateShipping({
  requestBody: { latitude: 40.6782, longitude: -73.9442, order_total: 598 },
});
```

```json Response
{
  "fee": 5.99,
  "zone_name": null,
  "tier_name": "Local (within 10 km)",
  "distance_meters": 8548,
  "is_free": false,
  "rate_source": "tier",
  "coordinates": { "latitude": 40.6782, "longitude": -73.9442 }
}
```

When you place the order, pass `shipping_latitude` + `shipping_longitude` so the server re-resolves
this fee and validates `shipping_amount` against it.

### With multi-carrier shipping (Shippo)

When the store has multi-carrier shipping connected, a destination `address_to` plus a `parcel`
returns live carrier rates for the shopper to choose from. The response then carries `rates[]` and
`rate_source: "shippo"`.

```typescript
const quote = await storefront.shipping.calculateShipping({
  requestBody: {
    latitude: 40.748, longitude: -73.985, order_total: 598,
    address_to: { street1: '350 5th Ave', city: 'New York', state: 'NY', zip: '10118', country: 'US' },
    parcel: { length: '10', width: '8', height: '4', distance_unit: 'in', weight: '2', mass_unit: 'lb' },
  },
});
```

```json Response
{
  "fee": 5.99,
  "rate_source": "shippo",
  "rates": [
    { "rate_id": "0fd775faba6246a7…", "provider": "USPS", "service": "Ground Advantage", "amount": 10.43, "currency": "USD", "estimated_days": 5 },
    { "rate_id": "1d2a10def7874574…", "provider": "UPS",  "service": "2nd Day Air",      "amount": 25.71, "currency": "USD", "estimated_days": 2 }
  ],
  "coordinates": { "latitude": 40.748, "longitude": -73.985 }
}
```

The shopper picks from `rates[]`; `shipping_amount` becomes that rate's `amount`, and its `rate_id`
travels into the order as `shippo_rate_id`, which the server validates the amount against.

## 6. Reserving stock before checkout (optional)

Where checkout takes a while — an async payment flow, a multi-page wizard — a reservation holds the
stock so the shopper cannot be oversold partway through. Each hold expires by itself after
`ttl_seconds`. The call originates in the browser, so it takes a publishable key, and the
`variant_id` comes forward from the cart.

```typescript
const { reservation_ids } = await storefront.orders.reserveStock({
  requestBody: {
    items: [{ variant_id: 'e98631a9-7852-4fe8-8efe-988935d5922a', quantity: 2 }],
    ttl_seconds: 900,
  },
});
```

```json Response
{
  "reservations": [
    { "reservation_id": "a81b3a3d-f810-47f4-ac50-592c3f22482f", "variant_id": "e98631a9-7852-4fe8-8efe-988935d5922a", "quantity": 1 }
  ],
  "reservation_ids": ["a81b3a3d-f810-47f4-ac50-592c3f22482f"],
  "expires_in_seconds": 900
}
```

<Note>
  If the requested quantity isn't available, **nothing** is reserved and the call returns `409`.
  Reserving is optional — skip it for a fast synchronous checkout; the order itself still validates
  stock at creation.
</Note>

## 7. Placing the order (server, signed)

Order creation is a secret-key call, HMAC-signed and carrying an idempotency key. The idempotency key
is what makes a retried checkout safe: the same key returns the original order rather than a
duplicate. [HMAC Signing](/authentication#advanced-security-hmac-signing) has the helper.

The three orders below are the same cart — the 2 Galaxy Watches from step 2 — priced three ways:
base, with a promotion, then with a promotion and a gift card.

<Note>
  Order items take `variant_id` (the exact SKU the shopper picked) or `product_id` (which resolves
  the product's default variant). When both are sent, `variant_id` wins. On a multi-variant product,
  dropping to `product_id` at checkout can order a different variant than the one in the cart, so the
  `variant_id` added to the cart is the one to carry into the order line. See
  [Products and variants](/concepts#products-and-variants-which-id-to-send-where).
</Note>

### 7a. The base order

```typescript
import { createHmac } from 'crypto';

const timestamp = Math.floor(Date.now() / 1000);
const orderData = {
  customer_email: 'john.doe@example.com',
  customer_name: 'John Doe',
  shipping_address: { street: '350 Fifth Avenue', city: 'New York', state: 'NY', zip: '10118', country: 'US' },
  items: [
    { product_id: '0186665f-f0a1-4c79-976a-919b5b1c2daa', variant_id: 'e98631a9-7852-4fe8-8efe-988935d5922a', quantity: 2, unit_price: 299, total_price: 598 },
  ],
  subtotal: 598,
  shipping_amount: 5.99,
  discount_amount: 0,
  // With automatic tax enabled, omit tax_amount — Galactic Core calculates it for the
  // shipping destination. total_amount must be the FINAL tax-inclusive total
  // (subtotal + tax + shipping − discount); preview the tax first with the Tax preview
  // endpoint (see the Tax guide) so the storefront shows and submits the right total.
  // Here NY tax on $598 is $53.08, so total = 598 + 53.08 + 5.99 = 657.07.
  total_amount: 657.07,
  payment_status: 'pending',
};

// Sign with `${timestamp}.${JSON.stringify(body)}`, HMAC-SHA256, base64.
const sign = (body: object, ts: number) =>
  createHmac('sha256', process.env.TYBRITE_HMAC_SECRET)
    .update(`${ts}.${JSON.stringify(body)}`)
    .digest('base64');

const { order } = await server.orders.createOrder({
  idempotencyKey: `order-${customer.id}-${timestamp}`,
  xTimestamp: timestamp,
  xSignature: sign(orderData, timestamp),
  requestBody: orderData,
});
```

### 7b. The same order with a promotion applied

The cart subtotal of $598 clears the Spring Sale — 15% off (min $50) promotion
(`df290d89-0400-4b2c-aa56-11fcc486150c`). `storefront.promotions.calculatePromotionDiscount(...)`
quotes the discount; the order then carries it as `discount_amount` plus a `promotion_usages` entry,
which is what tracks the usage.

15% of $598 is $89.70, so the total becomes `subtotal − discount + shipping` = `598 − 89.70 + 5.99` =
$514.29.

```typescript
const ts2 = Math.floor(Date.now() / 1000);
const orderWithPromo = {
  ...orderData,
  discount_amount: 89.70,
  total_amount: 514.29, // 598 − 89.70 + 5.99
  promotion_usages: [
    { promotion_id: 'df290d89-0400-4b2c-aa56-11fcc486150c', discount_amount: 89.70 },
  ],
};

const { order: promoOrder } = await server.orders.createOrder({
  idempotencyKey: `order-${customer.id}-${ts2}`,
  xTimestamp: ts2,
  xSignature: sign(orderWithPromo, ts2),
  requestBody: orderWithPromo,
});
// promoOrder.discount_amount === 89.7  ·  promoOrder.total_amount === 514.29
```

### 7c. The same order with a gift card as well

The shopper also redeems gift card `GTSA-1B2C-3D4E-5F6G` ($100 balance) for $50 against this order,
as a `gift_card_redemption: { code, amount }` block with the $50 folded into `discount_amount`.

<Note>
  A gift card reduces the total as part of `discount_amount`. The server validates
  `total_amount === subtotal + tax + shipping − discount_amount`, and the discount it accepts is the
  sum of every real entitlement: promotions plus the gift card's redeemable amount. With subtotal
  598, shipping 5.99, the $89.70 promotion and a $50 gift card, `discount_amount` is $139.70 and
  `total_amount` is `464.29` (598 + 5.99 − 139.70). The gift card balance is drawn down by the
  redeemed amount once the order is created. A gift card sent with a `discount_amount` that omits it
  — leaving the total at $514.29 — reduces nothing, and over-claiming a card beyond its balance is
  rejected as `discount_invalid` (7d).
</Note>

```typescript
const ts3 = Math.floor(Date.now() / 1000);
const orderWithGiftCard = {
  ...orderWithPromo,
  discount_amount: 139.70,                                  // promo 89.70 + gift card 50
  total_amount: 464.29,                                     // 598 + 5.99 − 139.70
  gift_card_redemption: { code: 'GTSA-1B2C-3D4E-5F6G', amount: 50 },
};

const { order: gcOrder, post_processing_warnings } = await server.orders.createOrder({
  idempotencyKey: `order-${customer.id}-${ts3}`,
  xTimestamp: ts3,
  xSignature: sign(orderWithGiftCard, ts3),
  requestBody: orderWithGiftCard,
});
// gcOrder.total_amount === 464.29  ·  post_processing_warnings === []  (gift card + stock OK)
```

```json Response
{
  "order": {
    "id": "5d219a1e-a4cc-44ef-90b3-6d0d5b8659d5",
    "order_number": "ORD-1782073131609",
    "customer_id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
    "subtotal": 598,
    "shipping_amount": 5.99,
    "discount_amount": 139.7,
    "total_amount": 464.29,
    "currency": "USD",
    "order_status": "pending",
    "payment_status": "paid",
    "created_at": "2026-06-21T20:18:53.655+00:00"
  },
  "post_processing_warnings": []
}
```

<Tip>
  Reduced to its simplest case: a $50 gift card on a $250 cart is `discount_amount: 50`,
  `total_amount: 200`, and `gift_card_redemption: { code, amount: 50 }`. The shopper pays $200 and the
  card's balance drops by $50. (Verified live: a $50 redemption on a $239.98 cart plus $5.99 shipping
  produced `total_amount: 195.97`.)
</Tip>

### 7d. The two rejections

<Note>
  The server is the price authority. Order creation recomputes every item price from the live catalog
  and validates the claimed `discount_amount` against the promotions and gift card named on the
  order, so amounts computed client-side carry no weight. The two guards below are what a mismatch
  meets.
</Note>

A `total_amount` that does not equal `subtotal + tax + shipping − discount_amount` is rejected as
`400 price_mismatch` before the order is created — here the gift card is in `discount_amount` but the
total was left unchanged:

```typescript
// discount_amount includes the $50 gift card, but total_amount wasn't lowered to match
const bad = { ...orderWithGiftCard, total_amount: 514.29 }; // should be 464.29
await server.orders.createOrder({ /* …signed… */, requestBody: bad });
```

```json Response (400)
{
  "error": {
    "code": "price_mismatch",
    "message": "total_amount does not match subtotal + tax + shipping − discount",
    "details": "expected 464.29, got 514.29"
  }
}
```

Consistent total math is not on its own sufficient. The server recomputes the maximum discount the
claimed promotions and gift card actually grant and rejects a `discount_amount` above it as
`400 discount_invalid` — a discount with no promotion or gift-card balance behind it has a maximum of
`0`, which is why neither an invented discount nor a redemption beyond a card's balance lowers the
price:

```typescript
// $598 cart, but claim a $290 discount with no promotion (or an over-stated one)
const bogus = { ...orderData, discount_amount: 290, total_amount: 308 };
await server.orders.createOrder({ /* …signed… */, requestBody: bogus });
```

```json Response (400)
{
  "error": {
    "code": "discount_invalid",
    "message": "discount_amount exceeds the discount the claimed promotions/gift card actually grant",
    "details": "max legitimate discount 0.00, claimed 290.00"
  }
}
```

An unrecognized gift card behaves differently again: a paid order redeeming one is not rolled back.
The order is created, returns `201`, and the failure arrives in `post_processing_warnings` and
stamped onto `order.notes`.

```typescript
const withBadCard = { ...orderWithPromo, payment_status: 'paid', gift_card_redemption: { code: 'NOPE-0000-0000-0000', amount: 50 } };
const { order, post_processing_warnings } = await server.orders.createOrder({ /* …signed… */, requestBody: withBadCard });
// order.id exists (201) — but post_processing_warnings is NON-empty. Handle it.
```

```json Response (201)
{
  "order": {
    "id": "8a44f0d2-1e9b-4c5a-bf03-77a2c6e91b8d",
    "order_number": "ORD-1781955472200",
    "payment_status": "paid",
    "total_amount": 514.29,
    "notes": "[GIFT_CARD_REDEMPTION_FAILED] Gift card not found for this store"
  },
  "post_processing_warnings": [
    {
      "stage": "gift_card_redemption",
      "message": "Gift card redemption failed: Gift card not found for this store. The order was created but no gift card credit was applied. Please contact support."
    }
  ]
}
```

<Note>
  Stock reduction fails the same way: a paid order short on inventory still returns `201`, with a
  `{ "stage": "stock_reduction", ... }` warning and a `[STOCK_REDUCTION_PARTIAL]` note. A non-empty
  `post_processing_warnings` means the order was placed and a person needs to follow up on it.
</Note>

## 8. Taking payment (server, signed)

Payment initialization is also `sk` + HMAC + idempotency. The shopper is redirected to the returned
`checkout_url`, and the order is finalized from the provider's webhook. The amount charged is the
order's own `total_amount`, which already reflects any gift card folded into its `discount_amount`.

```typescript
const payment = await server.payments.initializePayment({
  idempotencyKey: `pay-${gcOrder.id}`,
  xTimestamp: Math.floor(Date.now() / 1000),
  xSignature: paymentSignature, // sign the payment body the same way as the order
  requestBody: {
    provider: 'stripe',
    amount: 464.29, // gcOrder.total_amount from step 7c
    currency: 'usd',
    email: 'john.doe@example.com',
    success_url: 'https://example.com/payment-success',
    cancel_url: 'https://example.com/payment-cancelled',
  },
});

// Redirect the shopper to payment.checkout_url
```

```json Response
{
  "success": true,
  "provider": "stripe",
  "type": "redirect",
  "reference": "PAY-61713784-F4TAOI",
  "checkout_url": "https://checkout.stripe.com/c/pay/cs_test_a1wk...",
  "session_id": "cs_test_a1wkhnXDJL6XPIzS3rjHUeF0PxUb7yu6Nxw8WJsXpjIg...",
  "expires_at": "2026-06-21T13:21:54.000Z"
}
```

<Note>
  When the provider confirms payment, the webhook handler patches the order to `paid`
  (`server.orders.updateOrder(...)`). Galactic Core then reduces stock, books the sale, and updates
  the customer's metrics, so none of that is orchestrated by the integration.
  [Webhooks & automation](/workflows/webhooks-automation) covers the handler.
</Note>

## 9. Fulfilment and tracking

Once the order is paid, the merchant buys the carrier label from their admin. Buying a label charges
the merchant's carrier account, marks the order shipped, stamps the order's `tracking_number`, and
fires an `order.shipped` webhook — it is a fulfilment action, not a storefront SDK call.

The carrier's own tracking page is the shortest route to shopper-visible tracking. When the label is
bought, the carrier tracking URL is saved on the order at `shipping_metadata.shippo.tracking_url`,
and rendering it as a link needs no API call:

```tsx
const trackingUrl = order.shipping_metadata?.shippo?.tracking_url;
{trackingUrl && <a href={trackingUrl} target="_blank" rel="noopener noreferrer">Track your package</a>}
```

For a status rendered inside the storefront instead, `trackShipment` returns the live status and
history to build a timeline from:

```typescript
const status = await storefront.shipping.trackShipment({ carrier: 'usps', number: order.tracking_number });
// → { carrier, tracking_number, status, eta, history: [...] }
```

The `order.shipped` webhook is the moment either of the above becomes available to show.
