The `CmsService` class (accessed via `client.cms`) reads a store's editorial content — blog posts and shoppable lookbooks — and records views against the shopper's session, so a sale can later be attributed to the content that led to it. It also captures signups: the newsletter, and merchant-defined lead forms.

## Blog Posts

### `listPosts`

Retrieve a paginated list of published blog posts, newest first. This is ideal for building a
"News" or "Magazine" section on your storefront. Only published posts are returned — there is no
status filter. Filter by category with the category **slug** (`category: 'buying-guides'`).

```typescript
const { posts, pagination } = await client.cms.listPosts({ category: 'buying-guides', limit: 10 });

posts.forEach(post => {
  console.log(`${post.title} — updated ${post.updated_at}`);
});
```

**Post Metadata:**
The listing response includes light metadata like `excerpt`, `featured_image`, `video` (an optional cover video; `featured_image` stays its poster and fallback), `slug`, and
`product_count` (how many products a shoppable post links to). For the full `content`, use `getPost`.

`?fields=` on the listing accepts the summary fields above. The article body (`content`) and its
embedded `products` and `lookbooks` are fetched per post and belong to `getPost`; asking for one of
them here returns `400` naming the field rather than omitting it silently.

Each post carries two timestamps. `created_at` is when it was first written; `updated_at` is when it
was last edited, by anyone and in any way — a merchant revising the text, or an automated change such
as a regenerated cover image. An article page that shows a revision date reads as current when the
text has been kept up to date, so rendering "Updated {date}" where `updated_at` is later than the
publication date is usually worth doing. `updated_at` is always set: on a post that has never been
revised it matches `created_at`.

### `getPost`

Retrieve the full content of a specific published blog post by its slug, including any linked
products for shoppable posts (each entry in the `products` array carries the product's `name`,
`sku`, `price`, `images`, and `display_type`). Returns `404` if no published post matches the slug.

An embedded product also carries **`variant_id`** — pass that to `client.cartWishlist.addToCart`,
which is keyed by variant rather than product, so a shoppable post can add to a basket without a
second call. `embed_id` identifies the placement rather than the product. A `productEmbed` block in
`content` is matched to its entry on `product_id`, which equals the block's `productId`; `block_id` is the
`id` of the content block an embed is anchored to and is `null` for embeds placed in the post editor. An
embed whose product is no longer available is omitted, so a post can return fewer products than were
authored.

`content` is an [Editor.js](https://editorjs.io) document: `{ time, version, blocks }`, or `null` for a
post with no body. Each block is `{ id, type, data }`, and the fields in `data` depend on `type`.

| `type` | `data` fields |
|---|---|
| `paragraph` | `text` (inline HTML) |
| `header` | `text` (inline HTML), `level` (1 to 4) |
| `list` | `style` (`ordered` or `unordered`), `items` |
| `quote` | `text`, `caption` (inline HTML), `alignment` |
| `delimiter` | none |
| `table` | `content` (rows of cells, each inline HTML), `withHeadings` |
| `warning` | `title`, `message` (inline HTML) |
| `image` | `url`, `caption`, `alt`, `size` (`small`, `medium`, `large`, `full`) |
| `gallery` | `images` (each `url`, `caption`, `alt`), `layout` (`2-col`, `3-col`, `4-col`) |
| `video` | `url`, `caption`, `type` (`upload` or `embed`), `embedCode` |
| `embed` | `service`, `source`, `embed`, `width`, `height`, `caption` |
| `productEmbed` | `productId`, `productName`, `productImage`, `productPrice`, `displayType` (`card`, `inline`, `minimal`) |

Headings are typed `header`. In a `list`, `items` holds plain strings in older posts and
`{ content, items, meta }` objects in current ones, where `content` is inline HTML and `items` nests a
sub-list; both forms occur. A renderer skips any block whose `type` it does not recognise, because new
block types can be added without a change to the API version.

Inline HTML is limited to `<b>`, `<i>`, `<u>`, `<a href>`, `<mark>`, `<code>` and `<br>`. Content is
returned as stored and is not sanitised on read, so a storefront sanitises inline HTML to that list
before inserting it into a page, and accepts only `http`, `https` and `mailto` URLs in `href`. The
example below uses DOMPurify for that step.

```typescript
const post = await client.cms.getPost({
  slug: 'best-tech-gifts-2026',
  fields: 'title,content,products,published_at', // Optional
  visitorId,                                     // Optional — see Attributing content views
  sessionId
});

// Walk the blocks in order; `content` is null for a post with no body
const clean = (html: string) =>
  DOMPurify.sanitize(html ?? '', {
    ALLOWED_TAGS: ['b', 'i', 'u', 'a', 'mark', 'code', 'br'],
    ALLOWED_ATTR: ['href'],
  });

const listItems = (items: Array<string | { content: string; items?: any[] }>): string =>
  items
    .map((item) =>
      typeof item === 'string'
        ? `<li>${clean(item)}</li>`
        : `<li>${clean(item.content)}${item.items?.length ? `<ul>${listItems(item.items)}</ul>` : ''}</li>`
    )
    .join('');

const html = (post.content?.blocks ?? [])
  .map((block) => {
    const d: any = block.data;
    switch (block.type) {
      case 'paragraph':
        return `<p>${clean(d.text)}</p>`;
      case 'header': {
        const level = Math.min(Math.max(d.level ?? 2, 1), 4);
        return `<h${level}>${clean(d.text)}</h${level}>`;
      }
      case 'list': {
        const tag = d.style === 'ordered' ? 'ol' : 'ul';
        return `<${tag}>${listItems(d.items ?? [])}</${tag}>`;
      }
      case 'quote':
        return `<blockquote>${clean(d.text)}${d.caption ? `<footer>${clean(d.caption)}</footer>` : ''}</blockquote>`;
      case 'delimiter':
        return '<hr>';
      case 'image':
        return `<img src="${d.url}" alt="${d.alt ?? ''}">`;
      default:
        return ''; // unrecognised block types are skipped
    }
  })
  .join('\n');

// Shoppable products embedded in the post
post.products?.forEach(p => console.log(`Featured: ${p.name} ($${p.price})`));
```

### `getRelatedPosts`

Posts related to a given one, ranked on the server. The ranking combines what the writing is about
with the topics two posts share and how recently each was published, and nudges a post from a
different category up between otherwise equal results. Returns `404` if no published post matches
the slug.

**Render `reason`, not `score`.** The list is ordered by a rank that includes the category nudge, so
the scores are not always decreasing — a post scoring `0.458` can sit above one scoring `0.511`. To
a reader that looks like a sorting fault, while `reason` ("Closely related subject") is something
they can act on.

The list is topped up to at least three entries when few posts qualify, since a shelf of one reads
as a fault rather than a short list. Topped-up entries score strictly below the weakest genuine match
and carry the reason "More from this blog". `degraded` is `true` when the post has no stored
relevance data yet — most often because it was just published — and the ranking used topics and
recency alone; the list is still returned.

```typescript
const related = await client.cms.getRelatedPosts({
  slug: 'best-tech-gifts-2026',
  limit: 4, // Optional, default 4
});

related.related.forEach(p => console.log(`${p.title} — ${p.reason}`));
```

```json Response

    "slug": "top-3-premium-tech-picks-for-2026",
    "title": "Top 3 Premium Tech Picks for 2026"
```

### `getTrendingPosts`

The posts being read most, ranked by reads per day over a recent window.

The window widens — 7 days, then 21, 45 and 90 — until enough posts qualify, and the one that was
used comes back as `window_days`. A blog that publishes occasionally has quiet weeks, and a list
that is empty half the time is less useful than one describing a longer period honestly. Show the
period beside the list rather than calling everything "this week".

`reads_per_day` is normalised by the window, so the figure stays comparable as the window widens. It
orders the list; it is not a view counter and reads oddly if shown as one.

```typescript
const trending = await client.cms.getTrendingPosts({ limit: 6 });

console.log(`Most read over the last ${trending.window_days} days`);
trending.posts.forEach(p => console.log(p.title));
```

```json Response
{
  "posts": [
    {
      "id": "154000f5-0dce-4c1e-aacc-873ccb8aab00",
      "title": "Best Tech Gifts 2026",
```

## Attributing content views

`getPost` and `getLookbook` both accept a visitor and a session identifier, and record the view
against them. That is what lets the merchant see which posts and lookbooks drive sales rather than
just traffic — and it is the first half of the content funnel: pass the same `content_id` (with
`content_type`) in the order's `attribution` at checkout and the sale is credited back to the
content the shopper came from.

| Parameter | Description |
| :--- | :--- |
| `visitorId` | Your stable per-visitor identifier — the same one you use for storefront analytics. Also accepted as the `x-visitor-id` header, which takes precedence. |
| `sessionId` | The shopper's browsing session. Also accepted as the `x-session-id` header, which takes precedence. |

Both are optional. When you omit them the view still counts, but it is attributed to a coarse
fallback derived from the request, so repeat views by one shopper may not group together.

Lookbooks are curated collections of lifestyle images linked to specific products, perfect for "Shop the Look" features.

### `getLookbook`

Retrieve the full details of a published lookbook by its slug, including its ordered image gallery
and the shoppable **hotspots** placed on each image. Returns `404` if no published lookbook matches
the slug.

Each lookbook exposes `status` (always `"published"` from the public API) and `collection_id` — the
product collection that backs the lookbook, or `null` if it is standalone. The gallery lives under
`images[]`, where each image has a `url` and a `hotspots[]` array tagging the products featured at
specific points in the photo (your "Shop the Look" markers).

A hotspot gives `x` and `y` as percentages of the image's width and height from the top-left, so the
marker lands correctly at any display size, plus an optional `label` and the resolved `product`. The
product carries **`variant_id`** — pass that to `client.cartWishlist.addToCart`, which is keyed by
variant rather than product, so a marker can be added to a basket without a second call. Send a shopper
who wants a different size or colour to the product page instead. A hotspot whose product is no longer
available is omitted from the response, so an image can return fewer hotspots than were authored.

```typescript
const lookbook = await client.cms.getLookbook({
  slug: 'workspace-essentials',
  fields: 'title,description,images,collection_id,status' // Optional
});

// Render each gallery image and its shoppable hotspots
lookbook.images.forEach(image => {
  image.hotspots.forEach(({ x, y, label, product }) => {
    // x and y are percentages, so position the marker directly.
    console.log(`${label ?? product.name} at ${x}%/${y}% — add ${product.variant_id} to cart`);
  });
});
```

## Newsletter

### `subscribeNewsletter`

Capture a newsletter signup from your storefront. The email address is the identity, so this works for both anonymous visitors and signed-in shoppers (a signed-in storefront prefills the email field). When the merchant has connected a marketing tool, subscribers are synced to their chosen list automatically.

```typescript
const result = await client.cms.subscribeNewsletter({
  requestBody: {
    email: 'shopper@tybritelabs.com',
    source: 'post:summer-style-guide', // optional: where they signed up
  },
});

// result.subscribed === true
// result.already_subscribed === false on a fresh signup, true on a repeat
```

```json Response
{
  "subscribed": true,
  "already_subscribed": false
}
```

It is **safe to call repeatedly** — re-subscribing the same email returns `200` with `already_subscribed: true` and never creates a duplicate; a brand-new signup returns `201`. This endpoint accepts both **publishable** and **secret** keys (it's a storefront write, like cart), so you can call it directly from the browser.

## Lead Forms

A lead form is a signup form the merchant defines: a title, questions beyond the email address, consent wording and an optional challenge. A storefront reads the definition with `getLeadForm`, draws the form from it, and posts the answers with `submitLeadForm`. The [Lead forms guide](/lead-forms) describes the form definition, spam protection and server-side use in full.

### `getLeadForm`

Retrieve the published definition of a lead form by its slug. The response lists the fields in display order, the consent wording for the email and SMS checkboxes, whether a challenge is asked for, and the name of the hidden field to leave empty.

```typescript
const form = await client.cms.getLeadForm({ slug: 'spring-lookbook' });

form.fields.forEach(field => {
  console.log(`${field.label} (${field.type})${field.required ? ' *' : ''}`);
});
```

```json Response
{
  "slug": "spring-lookbook",
  "title": "Get the spring lookbook",
  "description": "Enter your email and we will send the lookbook.",
  "submit_label": "Send it to me",
  "success_message": "Thanks, check your inbox.",
  "double_opt_in": false,
  "fields": [
    { "name": "first_name", "label": "First name", "type": "text", "required": true, "placeholder": "Jane" },
    { "name": "interests", "label": "Interests", "type": "multiselect", "required": false, "options": ["Womenswear", "Menswear", "Accessories"] }
  ],
  "consents": { "email": { "text": "I agree to receive emails from this store." } },
  "captcha": { "available": false, "required": false, "on_demand": false },
  "hp_field": "website_url"
}
```

A form that is a draft, archived or unknown answers `404`. The email address is always collected and is not listed in `fields`. `redirect_url` appears when the merchant set one. The definition carries no per-visitor value, so it is cached.

### `createLeadFormToken`

Issue a token for one visit to a lead form. Request it when the form is shown and send it back unchanged as `form_token` with `submitLeadForm`. A submission carrying a token that is not valid for this form, or that arrives within two seconds of the token being issued, is acknowledged and discarded.

```typescript
const { form_token } = await client.cms.createLeadFormToken({ slug: 'spring-lookbook' });
```

```json Response
{
  "form_token": "lf1.1792571234.4f3c9a2b7e1d0c85a6b3f2e9d8c7b6a5"
}
```


### `submitLeadForm`

Record a signup. `answers` is keyed by the `name` of each field, `consents` carries the checkbox states, and the email address is `email`.

```typescript
const result = await client.cms.submitLeadForm({
  slug: 'spring-lookbook',
  requestBody: {
    email: 'john.doe@example.com',
    answers: { first_name: 'John', interests: ['Menswear'] },
    consents: { email: true },
    source: 'footer',
  },
  idempotencyKey: crypto.randomUUID(), // optional
});
```

```json Response
{
  "submitted": true,
  "pending_confirmation": false,
  "message": "Thanks, check your inbox.",
  "submission_id": "7c1f6a52-3b0e-4d8e-9d55-0f4a9a2c3e11"
}
```

A first signup and a repeat signup by the same email return the same response. When the form uses double opt-in, `pending_confirmation` is `true` until the shopper confirms from the email they receive. Answers for keys the form does not define are ignored.

A refused submission returns `400` with `details.field` naming the answer and `details.reason` giving the cause: `invalid_email`, `invalid_value`, `invalid_phone`, `required`, `consent_required`, `captcha_required` or `captcha_failed`.

**Keys:** both **publishable** and **secret** keys are accepted. A secret key is called from a server, so the caller sends the shopper's address in `xForwardedShopperIp` for per-address limits to apply to the shopper rather than to the server; the value is ignored on a publishable key. The caller also sends the shopper's two-letter country in `xForwardedShopperCountry`: a submission from the European Economic Area, or from a country that is not known, is stored but never reported to advertising conversion partners.

**Idempotency:** repeating an `idempotencyKey` with the same body returns the original result without recording a second submission. The same key with a different body answers `409`.

## Response Codes

The read endpoints (posts, lookbooks, `getLeadForm`) are `GET`; `subscribeNewsletter` and `submitLeadForm` are `POST`. All accept both **publishable** and **secret** keys. Slug validation is enforced — empty or whitespace-only slugs return `400` without hitting the database.

| Code | Meaning |
| :--- | :--- |
| `200` | Success. |
| `400` | Empty slug, invalid slug format, malformed query parameters, or a lead form submission that fails validation. |
| `401` | Invalid or missing API key. |
| `403` | The store's plan does not include lead forms (`submitLeadForm`). |
| `404` | Post, lookbook or lead form not found. |
| `409` | `Idempotency-Key` reused with a different submission (`submitLeadForm`). |
| `429` | Rate limit exceeded. |
| `500` | Internal server error. |
| `503` | A required challenge could not be verified (`submitLeadForm`). |
