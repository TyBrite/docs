title: "Authenticated Session"
description: "Reference for the AuthenticationService class in the Tybrite SDK."
---

The `AuthenticationService` (accessed via `client.authentication`) creates shopper accounts and issues their sessions. It handles sign-up with email confirmation, sign-in by password or emailed code, password recovery, session refresh and sign-out.

Every customer-scoped operation across the SDK, on `client.customers`, `client.cartWishlist`, `client.giftCards` and `client.messaging` among others, takes the session's `access_token` as the `xAuthToken` header. The `access_token` is the store's sign-in token: it is issued by the store and environment of the API key that created the session, and no other store accepts it.

<Note>
  **Already using your own auth provider?** If your storefront authenticates through Auth0, Clerk, Cognito, Firebase, NextAuth, SSO, or any other external identity system, you don't need this service. Use [`CustomersService`](./CustomersService) to provision Galactic Core customer records directly from your backend. See [Customers and Auth](../../customers-and-auth) for the decision matrix.
</Note>

Every method on this service is called with a secret key (`tybrite_sk_*`) from your server; a publishable key answers `403`. `getCurrentUser` is the exception and accepts either key.

## The Customer Session Lifecycle

```
1. Customer registers          register → emailed code → verifyRegistration
   or signs in                 login | sendMagicLink → verifyOtp
   ↓
2. The response carries session.access_token and session.refresh_token
   ↓
3. The storefront stores both (httpOnly cookie preferred)
   ↓
4. Every customer-scoped API call passes the access_token as xAuthToken
   ↓
5. Before expires_at → refreshToken → store the NEW access_token and refresh_token
   ↓
6. The customer signs out → logout, then clear the stored tokens
```

A session is the object `{ access_token, refresh_token, expires_in, expires_at, token_type }`, and `token_type` is always `shopper`.

| Field | Meaning |
| --- | --- |
| `access_token` | The store's sign-in token. It lasts 15 minutes (`expires_in` is `900`). |
| `refresh_token` | An opaque string that begins with `gcsr_`. It is valid for 30 days from its last use and works once: each `refreshToken` call returns a replacement and the earlier token stops working. |
| `expires_at` | Unix time at which `access_token` stops being accepted. |

<Note>
  A customer-scoped call whose `xAuthToken` is expired, revoked, issued by another store or environment, or malformed answers `401 invalid_token`. The storefront refreshes the session once and treats the shopper as signed out if the refresh also fails.
</Note>

<Note>
  **On a marketplace key**, the session belongs to the marketplace, and `customer` in the responses below is `null` because a marketplace shopper has an account without a per-store customer record. A marketplace adds purchases made as a guest with an email address to the account only when `user.email_verified` is `true`, which is the case once the address has been confirmed.
</Note>

## Sign-up

### `register`

Start a customer account. `register` does not return a session: every call answers **`202 Accepted`** with the same body, whether the address is new or already has an account, and sends one email.

- A new address receives a confirmation code and, when `redirect_to` is allowed, a confirmation link.
- An address that already has an account receives a notice that an account exists, with directions to sign in or reset the password.

The account and the first session are created by [`verifyRegistration`](#verifyregistration). Until the address is confirmed no account exists, so the response reveals nothing about which addresses have one.

`password` is optional. An account created without one signs in by emailed code (`sendMagicLink`, then `verifyOtp`) and can set a password later with [`changePassword`](#changepassword).

`redirect_to` is the storefront page that receives the shopper from the email. The email appends `?link_token=<token>` to it, and the page passes that token to `verifyRegistration`. It must be on one of the store's allowed storefront origins, which the merchant sets in the dashboard; otherwise it is ignored and the email carries the code only.

The email must be a real, deliverable address. Disposable and placeholder domains (`example.com`, `test.com`, known throwaway-mail providers, and similar) are rejected with `400 invalid_email`.

A password must be 8 to 72 characters long, counted as characters, and must not appear on the list of commonly used passwords, which is compared without regard to case. A password that breaks the rule is refused with `400 weak_password`; `details.rule` identifies the rule.

| `details.rule` | Refused when |
| --- | --- |
| `too_short` | The password has fewer than 8 characters. |
| `too_long` | The password has more than 72 characters. |
| `common` | The password is on the list of commonly used passwords, for example `password123`. |

```text
{
  "error": {
    "code": "weak_password",
    "message": "Password must be at least 8 characters.",
    "details": { "rule": "too_short" }
  }
}
```

The password rule is evaluated before the email is looked up, so the refusal is identical whether or not the email already has an account. The other `400` codes are `invalid_request` for a missing `email` or a field of the wrong type and `invalid_email` for a malformed, disposable or placeholder address.

Pass `marketing_consent: true` when the sign-up form includes a marketing opt-in box and the customer checked it. It defaults to `false`: a customer is never subscribed to marketing without affirmative consent. The customer can change this later via `updateCustomer`.

```typescript
const pending = await client.authentication.register({
  requestBody: {
    email: 'john.doe@example.com',
    password: 'securePassword123',   // optional
    name: 'John Doe',                // optional
    phone: '+12125550142',           // optional
    marketing_consent: true,         // optional
    redirect_to: 'https://shop.example.com/account?link=register'   // optional
  }
});
// pending.status === 'verification_required'
```

```json Response (202)
{
  "status": "verification_required",
  "email": "john.doe@example.com",
  "expires_in": 900
}
```

| Field | Type | Description |
| --- | --- | --- |
| `status` | `string` | Always `verification_required`. |
| `email` | `string` | The address exactly as submitted. |
| `expires_in` | `integer` | Seconds for which the emailed code and link are valid (`900`). |

### `verifyRegistration`

Confirm the address and create the account. Send the six-digit code from the email with the `email` that registered, or send the `link_token` from the email's link on its own. Returns **`201 Created`** with the shopper, the customer record and the first session.

A code is valid for 15 minutes and is accepted 5 times. A `link_token` is single-use and shares its code's expiry and attempts. When the address already had an account the code is consumed and the call answers `400 invalid_code`, the same as a wrong code.

A refused call carries the reason in `details.reason`:

| `details.reason` | Meaning |
| --- | --- |
| `expired` | The code is more than 15 minutes old. |
| `too_many_attempts` | The code has been tried 5 times. |
| `wrong` | Any other mismatch. |

```typescript
// From the code screen
const { user, customer, session } = await client.authentication.verifyRegistration({
  requestBody: { email: 'john.doe@example.com', code: '123456' }
});

// Or from the link: /account?link_token=...
await client.authentication.verifyRegistration({
  requestBody: { link_token: new URLSearchParams(location.search).get('link_token')! }
});
```

```json Response (201)
{
  "message": "Registration successful",
  "user": {
    "id": "df648f68-39b3-4ba6-9be2-ff0a9393c02b",
    "email": "john.doe@example.com",
    "email_confirmed": true,
    "email_verified": true,
    "has_password": true
  },
  "customer": {
    "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
    "name": "John Doe",
    "email": "john.doe@example.com",
    "phone": "+12125550142",
    "tier": "bronze",
    "total_purchases": 0,
    "created_at": "2026-06-20T11:36:54.174303+00:00"
  },
  "session": {
    "access_token": "eyJ...<redacted>.signature",
    "refresh_token": "gcsr_Zm9vYmFyYmF6cXV4MTIzNDU2Nzg5MGFiY2RlZmdoaWo",
    "expires_in": 900,

}
```

```json Response (400)
{
  "error": {
    "code": "invalid_code",
    "message": "That code is not valid. Check it, or ask for a new one.",
    "details": { "reason": "expired" }
  }

```

**Response shape:**

| Field | Type | Description |
| --- | --- | --- |
| `user` | `object` | The shopper's sign-in identity: `id`, `email`, `email_confirmed`, `email_verified`, `has_password`. |
| `customer` | `object \| null` | The store-scoped customer profile. `null` on a marketplace key. |
| `session` | `object` | `{ access_token, refresh_token, expires_in, expires_at, token_type }` |

### `resendRegistration`

Send a new confirmation code and link to an address that registered and has not yet confirmed. The earlier code stops working. The call answers **`202 Accepted`** with the same body as `register` for every address, and sends one email: a fresh confirmation for a pending registration, or the notice that an account exists when the address already has one.

At most one email per address is sent every 60 seconds and five an hour. A call past that is answered `202` and sends nothing.

```typescript
await client.authentication.resendRegistration({
  requestBody: { email: 'john.doe@example.com' }
});
```

```json Response (202)
{
  "status": "verification_required",
  "email": "john.doe@example.com",
  "expires_in": 900
}
```

## Sign-in

### `login`

Authenticate an existing customer with email and password. Returns **`200 OK`**.

Every refusal that depends on the account answers `401 invalid_credentials` with the same body: an address with no account, a wrong password, an account that has not been confirmed, a disabled account, and an account that has no password. `401 password_reset_required` is returned only after the correct password, for an account that must set a new one through [`forgotPassword`](#forgotpassword) and [`resetPassword`](#resetpassword). Repeated wrong passwords lock an account for a short period, during which every call for it answers `429 rate_limited` with `Retry-After`.

```typescript
const { message, user, customer, session } = await client.authentication.login({
  requestBody: {
    email: 'john.doe@example.com',
    password: 'securePassword123'
  }
});

// Persist for subsequent customer-scoped calls
localStorage.setItem('tybrite_access_token', session.access_token);
localStorage.setItem('tybrite_refresh_token', session.refresh_token);
```

```json Response (200)
{
  "message": "Login successful",
  "user": {
    "id": "df648f68-39b3-4ba6-9be2-ff0a9393c02b",
    "email": "john.doe@example.com",
    "email_confirmed": true,
    "email_verified": true,
    "has_password": true
  },
  "customer": {
    "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
    "name": "John Doe",
    "email": "john.doe@example.com",
    "phone": "+12125550142",
    "tier": "bronze",
    "total_purchases": 0,
    "created_at": "2026-06-20T11:36:54.174303+00:00"
  },

    "access_token": "eyJ...<redacted>.signature",
```

### `sendMagicLink`

Send a one-time sign-in code, and a link carrying it, to an address that has an account. Any account can sign in this way, with or without a password. The code is six digits and is valid for 15 minutes. The call answers **`202 Accepted`** with the same body for every address; an address without an account receives no email, and no account is created.

Sign-in by code is on for every store unless the merchant switches it off. `store.auth.passwordless` in the store information (`client.system.getStoreInfo`) reports the setting, and while it is `false` this method and `verifyOtp` answer `403 passwordless_disabled`.

`redirect_to` is the storefront page that receives the shopper from the email, which appends `?link_token=<token>` to it. It must be on one of the store's allowed storefront origins; otherwise it is ignored and the email carries the code only.

At most one email per address is sent every 60 seconds and five an hour. A call past that is answered `202` and sends nothing.

```typescript
await client.authentication.sendMagicLink({
  requestBody: {
    email: 'john.doe@example.com',
    redirect_to: 'https://shop.example.com/account?link=signin'   // optional
  }
});
```

```json Response (202)
{
  "status": "code_sent",
  "expires_in": 900
}
```

### `verifyOtp`

Complete sign-in with the code from the sign-in email, or with the `link_token` its link carries. Returns **`200 OK`** with the same shape as `login`: `message`, `user`, `customer` and `session`.

A code is valid for 15 minutes, is accepted 5 times and works once. A wrong, expired, used or unknown code answers `400 invalid_code` with no reason, and an address without an account answers the same way. This method never creates an account.

```typescript
const { user, customer, session } = await client.authentication.verifyOtp({

    email: 'john.doe@example.com',
```

## Password Management

### `forgotPassword`

Send a password reset code, and a link carrying it, to an address that has an account. The call answers **`202 Accepted`** with the same body for every address; an address without an account receives no email. The shopper completes the reset with [`resetPassword`](#resetpassword). The code is six digits and is valid for 15 minutes.

`redirect_to` is the storefront page that receives the shopper from the email, which appends `?link_token=<token>` to it. It must be on one of the store's allowed storefront origins; otherwise it is ignored and the email carries the code only.

```typescript
await client.authentication.forgotPassword({
  requestBody: {
    email: 'john.doe@example.com',
    redirect_to: 'https://shop.example.com/reset-password'   // optional
  }
});
```

```json Response (202)
{
  "status": "code_sent",
  "expires_in": 900
}
```

### `resetPassword`

Set a new password with the code from the reset email, or with the `link_token` its link carries. Every earlier session of the account ends, the account is sent a notice that its password changed, and the response is a new session with the same shape as `login`. A reset also clears a `password_reset_required` state.

A wrong, expired or used code answers `400 invalid_code` with no reason. The new password follows the [password rule](#register) that applies to `register`; a password that breaks it is refused with `400 weak_password`.

```typescript
const { user, customer, session } = await client.authentication.resetPassword({
  requestBody: {
    email: 'john.doe@example.com',
    code: '123456',
    new_password: 'newSecurePassword456'
  }
});
```

### `changePassword`

Change the password of the signed-in shopper, or set one for an account that has none. Every other session of the account ends, the account is sent a notice that its password changed, and the response carries a new session for the caller. Returns **`200 OK`**.

`current_password` is required when the account has a password (`user.has_password` is `true`) and is checked first. A wrong one answers `401 invalid_credentials` and counts toward the account's lock. An account created for sign-in by emailed code has no password, so it omits `current_password`. The new password follows the [password rule](#register) that applies to `register`.

<Warning>
  `xAuthToken` is mandatory and must be the customer's own sign-in token (the `access_token` from a session). Server keys cannot stand in: this method changes the customer's login credentials and requires per-customer authorization.
</Warning>

```typescript
const token = localStorage.getItem('tybrite_access_token')!;

const { session } = await client.authentication.changePassword({
  xAuthToken: token,
  requestBody: {
    current_password: 'securePassword123',
    new_password: 'newSecurePassword456'
  }
});
```

```json Response (200)
{
  "message": "Password updated",
  "user": {
    "id": "df648f68-39b3-4ba6-9be2-ff0a9393c02b",
    "email": "john.doe@example.com",
    "email_confirmed": true,
    "email_verified": true,
    "has_password": true
  },
  "session": {
    "access_token": "eyJ...<redacted>.signature",
    "refresh_token": "gcsr_Zm9vYmFyYmF6cXV4MTIzNDU2Nzg5MGFiY2RlZmdoaWo",
    "expires_in": 900,
    "expires_at": 1781959913,
    "token_type": "shopper"
  }
}
```

## Session Utilities

### `refreshToken`

Exchange a refresh token for a new session. Returns **`200 OK`**. The refresh token works once: the response carries a replacement, and the earlier token stops working the moment the new one is issued. Store the new `access_token` and `refresh_token` on every refresh.

A refresh that cannot be honoured answers `401 invalid_refresh_token`: the token has expired, its session ended through `logout` or a password change, it belongs to another store or environment, or it was presented a second time. Presenting a used token again ends its whole session. Two refreshes with the same token at once therefore leave one of them refused, so a storefront serialises refreshes per session. On `invalid_refresh_token` the shopper is signed out.

```typescript
const { session } = await client.authentication.refreshToken({
  requestBody: {
    refresh_token: localStorage.getItem('tybrite_refresh_token')!
  }
});

localStorage.setItem('tybrite_access_token', session.access_token);
localStorage.setItem('tybrite_refresh_token', session.refresh_token);
```

```json Response (200)
{
  "message": "Token refreshed successfully",
  "session": {
    "access_token": "eyJ...<redacted>.signature",
    "refresh_token": "gcsr_dGhpc2lzYXJlcGxhY2VtZW50dG9rZW4xMjM0NTY3ODkw",
    "expires_in": 900,
    "expires_at": 1781959913,
    "token_type": "shopper"
  }
}
```

<Tip>
  Schedule the refresh shortly before `expires_at`, or refresh once when a customer-scoped call answers `401 invalid_token`. Refreshing ahead of expiry avoids cart and wishlist write failures during checkout.
</Tip>

---

### `logout`

End a session. Send the `refresh_token` of the session: the whole session is revoked, so no refresh token issued since the sign-in works again. The call answers **`204 No Content`** for every request, including a refresh token that is unknown or already ended, so a storefront can call it whenever a shopper leaves. An access token already issued stays valid until its `expires_at`, at most 15 minutes.

```typescript
await client.authentication.logout({
  requestBody: { refresh_token: localStorage.getItem('tybrite_refresh_token')! }
});

localStorage.removeItem('tybrite_access_token');
localStorage.removeItem('tybrite_refresh_token');
```

### `getCurrentUser`

Return the signed-in shopper and their customer record, read from the sign-in token. Also routed as `GET /v1/auth/me`. Returns **`200 OK`** with `{ user, customer }`. `customer` is `null` on a marketplace key.

<Warning>
  `xAuthToken` is mandatory and must be the customer's own sign-in token. A token that is expired, revoked, issued by another store or environment, or malformed answers `401 invalid_token`.
</Warning>

```typescript
const token = localStorage.getItem('tybrite_access_token')!;

const { user, customer } = await client.authentication.getCurrentUser({
  xAuthToken: token
});

console.log(`Logged in as: ${user.email} (customer id: ${customer.id})`);
```

```json Response (200)
{
  "user": {
    "id": "df648f68-39b3-4ba6-9be2-ff0a9393c02b",
    "email": "john.doe@example.com",
    "email_confirmed": true,
    "email_verified": true,
    "has_password": true
  },
  "customer": {
    "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
    "name": "John Doe",
    "email": "john.doe@example.com",
    "phone": "+12125550142",
    "tier": "bronze",
    "total_purchases": 0,
    "created_at": "2026-06-20T11:36:54.174303+00:00"
  }
}
```

<Note>
  `getCurrentUser` returns just enough to identify the customer. For the complete profile, including addresses, store metrics, purchase history and status, call [`CustomersService.getCustomer`](./CustomersService#getcustomer); the same `xAuthToken` works there. Profile edits live on `CustomersService` via [`updateCustomer`](./CustomersService#updatecustomer).
</Note>

## Claiming an account from a guest order

A guest who checks out without an account can set a password on the order confirmation page and keep the order. A secret-key `createOrder` call for a guest returns a one-time `claim_token` on the order; the storefront's server passes it to `claimAccountFromOrder` together with the password the shopper chose. The token is a credential and is shown once.

### `claimAccountFromOrder`

Create an account from a guest order.

Turn a guest order into an account. The guest sets a password on the order confirmation page and
receives a signed-in session for a new account that owns that order and saves its shipping address.

The credential is the `claim_token` returned once by `POST /v1/orders` when the order was created.
The account is bound to the order's email address; no other address can be claimed. A token works once
and expires (7 days by default; the store can change this or turn the feature off).

The token proves possession of the order confirmation, not of the mailbox, so the account starts with
`email_verified: false`. It becomes verified when the shopper signs in with an emailed code or resets
their password; at that moment every session issued before is revoked and, unless the password was just
replaced, a new password is required at the next password sign-in.

**Refusals.** A token that is wrong, spent, expired, for another store or environment, or for an
unknown order answers `404 not_found`, identically. Once the token is valid:
`409 account_exists` when the address already has an account at this store (nothing is linked; the
shopper signs in), and `409 claim_unavailable` when the address already has other orders with this
store (the shopper registers with an emailed code, which proves the mailbox and brings the orders
together). A weak password is `400 weak_password`, checked first, as on registration.

Only the order for this token is claimed. Other guest orders for the same address are not linked.

**Secret key required.** This endpoint requires a secret key (`tybrite_sk_*`), called from the
storefront's server. Publishable keys answer `403 forbidden`.

**Attempt limits:** 10 attempts per order per hour and 600 per store per hour; past either, the call
answers `429 rate_limited` with a `Retry-After` header. After 10 wrong tokens an order's token is
locked.

```typescript
const result = await client.authentication.claimAccountFromOrder({
  requestBody: {
    order_id: '7c1f3b0a-9d2e-4a5b-8c6d-0e1f2a3b4c5d',
    claim_token: 'gcclaim_Zm9vYmFyYmF6cXV4MTIzNDU2Nzg5MGFiY2RlZmdoaWo',
    password: 'SecurePassword123!'
  }
});
```

```json Response
{
  "message": "Account created",
  "user": {
    "id": "8d6a1c52-0b8f-4e63-a1f4-2c9d7e5b3a10",
    "email": "john.doe@example.com",
    "email_confirmed": true,
    "email_verified": false,
    "has_password": true
```

## Full Lifecycle Example

This walks the customer from sign-up, through a cart mutation and checkout, to logout, showing where `xAuthToken` flows.

```typescript
import { Tybrite } from '@tybrite-labs/sdk';

const client = new Tybrite({ apiKey: process.env.TYBRITE_SECRET_KEY });

// 1. SIGN UP — the address is confirmed before the account exists
await client.authentication.register({
  requestBody: { email: 'john.doe@example.com', password: 'securePassword123', name: 'John Doe' }
});
const { customer, session } = await client.authentication.verifyRegistration({
  requestBody: { email: 'john.doe@example.com', code: '123456' }   // the code from the email
});

const token = session.access_token;

// 2. CART — customer-scoped operations carry xAuthToken
await client.cartWishlist.addToCart({
  xAuthToken: token,
  requestBody: {
    customer_id: customer!.id,
    variant_id: '9a47e047-b1b6-4c35-9617-820629e22e04',
    quantity: 2
  }
});

// 3. CHECKOUT — order creation is sk-only + idempotent + HMAC-signed
//    (uses your server-side secret key, not the customer's token)
const order = await client.orders.createOrder({
  idempotencyKey: crypto.randomUUID(),
  xTimestamp: timestamp,
  xSignature: signature,
  requestBody: { customer_id: customer!.id, items: [/* ... */] }
});

// 4. REFRESH — before access_token expires
const { session: refreshed } = await client.authentication.refreshToken({
  requestBody: { refresh_token: session.refresh_token }
});

// 5. LOGOUT — end the session server-side
await client.authentication.logout({
  requestBody: { refresh_token: refreshed.refresh_token }
});
```

### Response Codes

| Method | Success | Notable Errors |
| --- | --- | --- |
| `register` | **202 Accepted** | `400` `invalid_request`, `invalid_email` or `weak_password`; `429` `rate_limited` |
| `verifyRegistration` | **201 Created** | `400` `invalid_code` with `details.reason`; `429` |
| `resendRegistration` | **202 Accepted** | `400` `invalid_email`; `429` |
| `login` | **200 OK** | `401` `invalid_credentials` or `password_reset_required`; `429` |
| `sendMagicLink` | **202 Accepted** | `400` `invalid_email`; `403` `passwordless_disabled` |
| `verifyOtp` | **200 OK** | `400` `invalid_code`; `403` `passwordless_disabled` |
| `forgotPassword` | **202 Accepted** | `400` `invalid_email` |
| `resetPassword` | **200 OK** | `400` `invalid_code` or `weak_password` |
| `changePassword` | **200 OK** | `400` `weak_password`; `401` `invalid_token` or `invalid_credentials` |
| `refreshToken` | **200 OK** | `401` `invalid_refresh_token` |
| `logout` | **204 No Content** | none for a well-formed call |
| `getCurrentUser` | **200 OK** | `401` `invalid_token` |

### Attempt limits

Attempts are limited by where they come from. Every attempt counts, successful or not, and an address with no account is treated identically, so a `429` says nothing about whether an account exists. A refused call returns `429 rate_limited` with a `Retry-After` header giving the seconds to wait.

With a **secret key** (a storefront's server, whose address is not the shopper's), each method is limited per store and email address. Past the threshold the account is not refused; it is slowed to one attempt per interval, and `Retry-After` gives the seconds until the next one is accepted.

| Method | Per store and email, 15 minutes | Then one attempt every |
| --- | --- | --- |
| `login` | 10 | 15 seconds |
| `verifyRegistration`, `verifyOtp`, `resetPassword` | 10 | 30 seconds |
| `register` | 5 | 60 seconds |
| `resendRegistration`, `sendMagicLink`, `forgotPassword` | 5 | 60 seconds |

With a **publishable key** (a browser), attempts are limited per calling address: 20 per address and email, and 60 per address across all emails, in 15 minutes.

Across every store and address, a higher per-email threshold slows an attack spread over many sources:

| Method | Per email across all stores, 15 minutes | Then one attempt every |
| --- | --- | --- |
| `login` | 50 | 10 seconds |
| `verifyRegistration`, `verifyOtp`, `resetPassword` | 20 | 30 seconds |
| `register` | 20 | 60 seconds |
| `resendRegistration`, `sendMagicLink`, `forgotPassword` | 10 | 60 seconds |

Session calls are limited per token: `refreshToken` and `logout` 20 per refresh token and `changePassword` 5 per sign-in token in 15 minutes, `getCurrentUser` 120 per sign-in token per minute.

<Note>
  **Token Lifetime:** Access tokens are valid for 15 minutes. A storefront calls `refreshToken` before `expires_at`, or once on `401 invalid_token`, and stores the replacement pair each time.
</Note>
