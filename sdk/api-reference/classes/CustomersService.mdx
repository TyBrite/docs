The `CustomersService` class (accessed via `client.customers`) exposes the customer record as a first-class API resource — meant for integrations that manage authentication outside Galactic Core.

<Note>
  **Two integration paths.** If your storefront uses Galactic Core's built-in auth (`/v1/auth/register`, `/v1/auth/login`, etc.), prefer the [`AuthenticationService`](./AuthenticationService) — it creates and links the customer record for you. Use `CustomersService` when you're bringing your own identity provider (Auth0, Clerk, Cognito, Firebase, NextAuth, SSO, etc.) and want to provision the Galactic Core customer record directly from your backend. See [Customers and Auth](../../customers-and-auth) for the full decision matrix.
</Note>

<Note>
  **Sandbox isolation:** Customer records created with a `tybrite_sk_test_*` key exist only in the sandbox environment and are never visible to production keys. Every response includes a `Tybrite-Environment: sandbox | production` header confirming which environment resolved.
</Note>

## Profile Management

<Note>
  A customer carries a `custom_fields` array — fields the merchant defined themselves, such as a VAT registration. See [Custom Fields](/custom-fields).
</Note>

### `createCustomer`

Provision a Galactic Core customer record. The customer exists immediately and can place orders, hold a cart, leave reviews, etc. — but no Galactic Core login credentials are created. Authentication remains the responsibility of your external identity provider.

Pass `external_id` to store your upstream user identifier (Auth0 `sub`, Clerk `user.id`, etc.). It's unique per store + environment, so subsequent reads can look up the Galactic Core customer by that identifier without keeping a side-table.

Pass `marketing_consent` to record whether the customer opted in to marketing communications. It defaults to `false` (opt-in) — only set it to `true` when the customer affirmatively checks a marketing opt-in box on your storefront. When `true`, the customer becomes eligible to be subscribed to the store's connected marketing tools.

<Note>
  **Secret Key only.** Call this from a secure server-side environment — typically a webhook or post-signup hook in your identity provider.
</Note>

```typescript
const result = await client.customers.createCustomer({
  requestBody: {
    email: 'jane.doe@tybritelabs.com',
    name: 'Jane Doe',
    phone: '+12125550123',
    address: '350 Fifth Avenue, New York, NY 10118',
    external_id: 'auth0|66a3f8c2b1d9c204a1f7e3d1', // your upstream user id
    marketing_consent: true, // they ticked the marketing opt-in box
  }
});
const customer = result.customer;
// Store customer.id alongside your upstream user record for future calls.
```

**Response `201`:**

```json
{
  "customer": {
    "id": "0adffe56-ccc7-4868-bb4c-0f0ca5db117f",
    "name": "Jane Doe",
    "email": "jane.doe@tybritelabs.com",
    "phone": "+12125550123",
    "address": "350 Fifth Avenue, New York, NY 10118",
    "status": "active",
    "tier": "bronze",
    "join_date": "2026-06-20",
    "external_id": "auth0|66a3f8c2b1d9c204a1f7e3d1",
    "marketing_consent": true,
    "total_purchases": 0,
    "last_purchase": null,
    "store_credit_balance": 0,
    "created_at": "2026-06-20T11:37:12.876998+00:00",
    "updated_at": "2026-06-20T11:37:12.876998+00:00",
    "store_metrics": null
  }
}
```

<Note>
  A newly created customer starts at the `bronze` `tier` with no purchase history, so `last_purchase` and `store_metrics` are `null` until their first order. The `tier` rises through `silver`, `gold`, and `platinum` as the customer's lifetime spend grows.
</Note>

<Note>
  The customer's marketing opt-in can be changed later via `updateCustomer` (e.g. when a
  signed-in shopper toggles email preferences in their account). Pass
  `requestBody: { marketing_consent: false }` to opt them out.
</Note>

<Note>
  `createCustomer` returns `{ customer }`. `getCustomer` returns the customer fields at the top level.
</Note>

### `getCustomer`

Retrieve a customer's profile, including store metrics and purchase history. This is the endpoint your "My Account" page calls. The response includes `store_credit_balance` — the customer's redeemable store-credit balance, which can be applied at checkout via `apply_store_credit` on `createOrder`.

Sign an `xExternalAuth` assertion in your backend (see [Customers and Auth](../../customers-and-auth) for the signing helper) and pass it through:

```typescript
const assertion = signCustomerAssertion(upstreamUserId, process.env.GC_HMAC_SECRET);

const customer = await client.customers.getCustomer({
  id: gcCustomerId,
  xExternalAuth: assertion,
  fields: 'name,email,store_metrics.total_spent'
});
```

<Accordion title="Using Galactic Core auth, or a raw provider token, instead?">
  If your storefront authenticates customers through Galactic Core (Path A), pass the customer's session JWT as `xAuthToken` in place of `xExternalAuth`:

  ```typescript
  const customer = await client.customers.getCustomer({
    id: gcCustomerId,
    xAuthToken: customerSession.access_token,
  });
  ```

  If you'd rather not sign an assertion, pass the raw token from your identity provider (for example a Firebase ID token) as `xIdpToken`. Galactic Core forwards it to your store's configured Auth verifier, which validates it and returns the identity:

  ```typescript
  const customer = await client.customers.getCustomer({
    id: gcCustomerId,
    xIdpToken: firebaseIdToken,
  });
  ```

  `xIdpToken` is fail-closed: if the verifier rejects the token or is unreachable, the request is unauthenticated (`401`). It requires an Auth verifier to be configured for the store.

  Provide exactly one of `xAuthToken`, `xExternalAuth`, or `xIdpToken`. More than one → `400`. Mismatch with the path `id` → `403`.
</Accordion>

**Response `200`** — the customer fields are returned at the top level (not wrapped in a `customer` key):

```json
{
  "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
  "name": "Jane Doe",
  "email": "jane.doe@tybritelabs.com",
  "phone": "+12125550142",
  "address": null,
  "status": "active",
  "tier": "bronze",
  "join_date": "2026-06-20",
  "external_id": null,
  "marketing_consent": true,
  "total_purchases": 0,
  "last_purchase": null,
  "store_credit_balance": 0,
  "created_at": "2026-06-20T11:36:54.174303+00:00",
  "updated_at": "2026-06-20T11:36:54.174303+00:00",
  "store_metrics": null
}
```

<Note>
  `address`, `last_purchase`, and `store_metrics` are `null` until the customer has supplied an address and made a purchase. `tier` is one of `bronze` / `silver` / `gold` / `platinum`, derived from purchase history.
</Note>

### `updateCustomer`

Partially update a customer's profile. Only the fields you supply are modified. Typical caller: a "Save changes" button on the customer's account page.

The writable fields are `name`, `phone`, `address`, `status` (`active` or `inactive`) and `marketing_consent`. Any other field in `requestBody` — `external_id`, `tier` or a purchase total, for example — is ignored, and a body naming no writable field returns the customer unchanged.

`email` is writable only when the call is made with a secret key, from your storefront's server after it has verified the new address. With a publishable key, `email` is ignored like any other non-writable field, because guest orders are linked to a customer by email address. Changing `email` to an address another customer of the store already uses returns `409`.

```typescript
const assertion = signCustomerAssertion(upstreamUserId, process.env.GC_HMAC_SECRET);

const result = await client.customers.updateCustomer({
  id: gcCustomerId,
  xExternalAuth: assertion,
  requestBody: {
    address: '350 Fifth Avenue, New York, NY 10118',
    name: 'Jane Doe'
  }
});
const updated = result.customer;
```

**Response `200`** — the updated profile, wrapped in a `customer` key:

```json
{
  "customer": {
    "id": "15ecd58f-a8f8-49e4-9098-96f1fa8308e9",
    "name": "Jane Doe",
    "email": "jane.doe@tybritelabs.com",
    "phone": "+12125550199",
    "address": "350 Fifth Avenue, New York, NY 10118",
    "status": "active",
    "join_date": "2026-06-20",
    "external_id": null,
    "marketing_consent": true,
    "total_purchases": 0,
    "last_purchase": null,
    "store_credit_balance": 0,
    "created_at": "2026-06-20T11:36:54.174303+00:00",
    "updated_at": "2026-06-20T11:36:54.174303+00:00",
    "store_metrics": null
  }
}
```

<Accordion title="Using Galactic Core auth, or a raw provider token, instead?">
  ```typescript
  const result = await client.customers.updateCustomer({
    id: gcCustomerId,
    xAuthToken: customerSession.access_token,
    requestBody: { address: '350 Fifth Avenue, New York, NY 10118' }
  });
  // returns { customer: { ... } } — same response shape as above
  ```

  You can also pass a raw identity-provider token (for example a Firebase ID token) as `xIdpToken`, which Galactic Core forwards to your store's Auth verifier — fail-closed, so a rejected or unreachable verifier returns `401`:

  ```typescript
  const result = await client.customers.updateCustomer({
    id: gcCustomerId,
    xIdpToken: firebaseIdToken,
    requestBody: { address: '350 Fifth Avenue, New York, NY 10118' }
  });
  ```

  Provide exactly one of `xAuthToken`, `xExternalAuth`, or `xIdpToken`. More than one → `400`. Mismatch with the path `id` → `403`.
</Accordion>

<Note>
  `updateCustomer` returns `{ customer }`. Unwrap the `customer` key to get the resource.
</Note>


## Saved addresses

Let a signed-in shopper keep a personal address book — multiple billing and shipping addresses they can reuse at checkout instead of re-typing them every time. Pre-fill your checkout form from `listAddresses`, or pre-select the shopper's default shipping/billing address.

These are **customer-self** operations: they work with a **publishable key** (safe to call from the browser), but require the shopper's session token in `xAuthToken`. The token must resolve to the customer in the `id` path parameter, otherwise the call returns `403`.

<Note>
  **Single default per kind.** Setting an address as the default for shipping (`is_default_shipping`) or billing (`is_default_billing`) automatically clears any previous default of the same kind, so there's always at most one default shipping address and one default billing address.
</Note>

### `listAddresses`

Return the shopper's saved addresses, defaults first. Use this to render their saved addresses at checkout.

```typescript
const { addresses } = await client.customers.listAddresses({
  id: session.customer.id,
  xAuthToken: session.session.access_token,
});

const defaultShipping = addresses.find(a => a.is_default_shipping);
```

### `updateAddress`

Partially update a saved address — only the fields you supply are changed. Pass the address `id` as `addressId`.

```typescript
const { address } = await client.customers.updateAddress({
  id: session.customer.id,
  addressId: existingAddressId,
  xAuthToken: session.session.access_token,
  requestBody: {
    line2: 'Suite 200',
    is_default_billing: true,
  },
});
// returns { address: { id, customer_id, line2: 'Suite 200', is_default_billing: true, ... } }
//   (the full updated address, same shape as createAddress)
```

### `deleteAddress`

Remove an address from the shopper's address book.

```typescript
await client.customers.deleteAddress({
  id: session.customer.id,
  addressId: existingAddressId,
  xAuthToken: session.session.access_token,
});
// returns { success: true, message: 'Address deleted' }
```


## Subscribe & Save subscriptions

A shopper subscription is one shopper's acceptance of a [Subscribe & Save](/subscribe-save) offer: which items, how often, where to send them and how each delivery is paid. These are **customer-self** operations. They work with a publishable key and require the shopper's session token in `xAuthToken` (or `xExternalAuth`, never both); the token must resolve to the customer in the `id` path parameter, otherwise the call returns `403`. A subscription that belongs to another shopper reads as `404`.

### `listShopperSubscriptions`

List a shopper's Subscribe & Save subscriptions.

Return the signed-in shopper's Subscribe & Save subscriptions at this store, newest first
(at most 100). Each subscription lists its items, the interval, the date of the next delivery, the
saved card that is charged (when there is one) and the terms the shopper accepted.

**Customer-self access.** Works with a publishable key (safe from the
browser). Provide the shopper's session token in the `x-auth-token`
header (or the store's bring-your-own-auth assertion in `x-external-auth`);
it must resolve to the customer in the `{id}` path parameter, otherwise the
request returns `403`. A subscription that belongs to another shopper reads
as `404`.

```typescript
const result = await client.customers.listShopperSubscriptions({
  id: '2f9c1a7e-5b3d-4e8a-9c01-7d6e5f4a3b21',
  xAuthToken: shopperToken
});
```

### `updateShopperSubscription`

Change a Subscribe & Save subscription.

Change one thing about the shopper's subscription per request: the delivery interval, the
items, or where the deliveries go. A change to the items applies from the next delivery; a change to
the interval restarts the schedule from today. A change the offer or the store does not allow is refused with `400` or `409`
and a message the shopper can read: an interval the offer does not list, an item the offer does not
cover, or item changes the store has turned off.

Send exactly one group of fields:

- `interval_unit` with `interval_count`: the delivery interval, one of the offer's intervals.
- `items`: the full list of items for each delivery, 1 to 50 entries. Items left out are removed.
- `fulfillment_method` with `shipping_address_id` (one of the shopper's saved addresses) for delivery, or
  with `pickup_location_id` for pickup, and optionally `shipping_option_id`.

**Customer-self access.** Works with a publishable key (safe from the
browser). Provide the shopper's session token in the `x-auth-token`
header (or the store's bring-your-own-auth assertion in `x-external-auth`);
it must resolve to the customer in the `{id}` path parameter, otherwise the
request returns `403`. A subscription that belongs to another shopper reads
as `404`.

```typescript
const result = await client.customers.updateShopperSubscription({

  subscriptionId: '8d6a1c52-0b8f-4e63-a1f4-2c9d7e5b3a10',
  xAuthToken: shopperToken,
  requestBody: {
    interval_unit: 'week',
    interval_count: 6

});
```

### `pauseShopperSubscription`

Pause a Subscribe & Save subscription.

Pause the subscription so no delivery is created while it is paused. Send `until` to resume
automatically on that date, from tomorrow up to a year ahead; omit it to stay paused until the shopper
resumes. Only an active subscription can be paused, and not while a delivery is being prepared.

**Customer-self access.** Works with a publishable key (safe from the
browser). Provide the shopper's session token in the `x-auth-token`
header (or the store's bring-your-own-auth assertion in `x-external-auth`);
it must resolve to the customer in the `{id}` path parameter, otherwise the
request returns `403`. A subscription that belongs to another shopper reads
as `404`.

```typescript
const result = await client.customers.pauseShopperSubscription({
  id: '2f9c1a7e-5b3d-4e8a-9c01-7d6e5f4a3b21',
  subscriptionId: '8d6a1c52-0b8f-4e63-a1f4-2c9d7e5b3a10',
  xAuthToken: shopperToken,
  requestBody: {
    until: '2026-12-15'
  }
});
```

```json Response
{
```

## Saved payment methods

A card the shopper agreed to keep for later deliveries is listed without its number: brand, last four digits and expiry. `startShopperCardUpdate` returns a hosted page on which the shopper enters a replacement card for one subscription, so card details never reach the storefront.

### `startShopperCardUpdate`

Add a card to a Subscribe & Save subscription.

Start adding a replacement card for a subscription. The response is the payment processor's own
hosted page; the shopper enters the card there. When the processor confirms the card it is saved and
the subscription charges it for every later delivery, and a delivery that was waiting on a declined
card is retried with it. The shopper returns to the subscription's manage page afterwards.

A store whose processor cannot save cards answers `409`. At most 10 sessions can be started per
shopper per hour (`429`).

**Customer-self access.** Works with a publishable key (safe from the
browser). Provide the shopper's session token in the `x-auth-token`
header (or the store's bring-your-own-auth assertion in `x-external-auth`);
it must resolve to the customer in the `{id}` path parameter, otherwise the
request returns `403`. A subscription that belongs to another shopper reads
as `404`.

```typescript
const result = await client.customers.startShopperCardUpdate({
  id: '2f9c1a7e-5b3d-4e8a-9c01-7d6e5f4a3b21',
  subscriptionId: '8d6a1c52-0b8f-4e63-a1f4-2c9d7e5b3a10',
  xAuthToken: shopperToken
});
```


## Purchased items

Digital downloads, codes and licence keys, and event tickets are delivered once an order is paid. `listShopperFulfilments` lists the delivered items across orders, `revealShopperFulfilmentCodes` returns the codes of one delivery in clear, and `downloadShopperFulfilmentFile` answers with a redirect to a short-lived link to one file. See [What a store can sell](/what-a-store-can-sell).

### `listShopperFulfilments`

List a shopper's delivered items.

Return the downloads, codes, event tickets and services the shopper has bought, across their
orders, newest first. Each purchased unit is one entry, so an order line of three event tickets
lists three entries. An entry is `preparing` until the item is delivered, then `delivered`, and
`voided` after a refund or return.

A `digital` entry lists its files, each with a `download_url`. A `code` entry shows its codes
masked and a `reveal_url`; read the codes themselves with
`POST /v1/customers/{id}/fulfilments/{fulfilment_id}/reveal`. An `event_ticket` entry lists its
tickets with the text to encode as the QR code. A `service` entry carries the merchant's
confirmation note.

**Customer-self access.** Works with a publishable key (safe from the browser). Provide the
shopper's session token in the `x-auth-token` header (or the store's bring-your-own-auth
assertion in `x-external-auth`, never both); it must resolve to the customer in the `{id}` path
parameter, otherwise the request returns `403`. A Connect key needs the `fulfilment:read` scope.

```typescript
const result = await client.customers.listShopperFulfilments({
```

### `downloadShopperFulfilmentFile`

Download a file the shopper bought.

Answer `302` with a short-lived link to one file of a delivered `digital` entry. The response has
no body; follow the `Location` header to receive the file. Each request counts towards the
download limit and the access period the merchant set for the product.

Two ways to call it:

- **Link from the delivery email or the entry's `download_url`.** Pass the link token as the `t`
  query parameter. No API key and no shopper header is sent; the token is the credential, and
  sending a shopper header with it returns `400`. Requests are limited per address and per entry.
- **Shopper credentials.** Omit `t`, send the API key, and send the shopper's session token in
  `x-auth-token` (or the store's assertion in `x-external-auth`, never both). The shopper must be
  the buyer of the entry. A Connect key needs the `fulfilment:read` scope.

An entry or file that does not exist, a token that does not match and a shopper who is not the
buyer all answer the same `404`.

```typescript
const result = await client.customers.downloadShopperFulfilmentFile({
  fulfilmentId: '3b7c2f60-5d1a-4e8b-9c42-7a1d0e6f8b21',
  assetId: '0c9d4e21-7b3a-4f15-8e60-2a5b6c7d8e90',
  t: 'Zk3q9XvL2mPaT7uRw1Yb8A' // the link token from the delivery email
});
```

## Authentication Flow

The `getCustomer` and `updateCustomer` methods require the shopper to be identified in addition to your API key, by exactly one of three headers: a customer session JWT (`xAuthToken`, obtained via the `AuthenticationService` through `login` or `verifyOtp`), a bring-your-own-auth signed assertion (`xExternalAuth`), or a raw identity-provider token (`xIdpToken`) that Galactic Core forwards to your store's Auth verifier. See [Customers and Auth](../../customers-and-auth) for choosing between them.

<Warning>
  Never expose **Secret Keys** in client-side code. For browser-based customer portals, use a **Publishable Key** in combination with the customer's `xAuthToken`.
</Warning>

```typescript
// 1. Customer logs in via AuthenticationService
const session = await client.authentication.login({
  requestBody: { email: 'jane.doe@tybritelabs.com', password: '...' }
});
// returns { message: 'Login successful', user, customer, session }

// 2. Use the returned access_token for subsequent customer-scoped calls
const profile = await client.customers.getCustomer({
  id: session.customer.id,
  xAuthToken: session.session.access_token
});
// returns { id, name, email, tier: 'bronze', address, store_credit_balance, store_metrics, ... }
//   (customer fields at the top level — not wrapped in a `customer` key)
```

<Note>
  `createCustomer` is intentionally **Secret Key only** — it is an admin/CRM operation (e.g. bulk imports) and does not involve customer authentication. No `xAuthToken` is required or accepted.
</Note>

### Response Codes

| Code | Meaning |
|------|---------|
| `201` | Customer created successfully (`createCustomer`) |
| `400` | Invalid request — malformed body or missing required fields |
| `401` | Invalid API key, or missing/invalid `xAuthToken` |
| `403` | Forbidden — the customer token does not match the `customer_id` in the path |
| `404` | Customer not found |
| `409` | Duplicate email at this store (on `createCustomer`, or an `email` change on `updateCustomer`) |
