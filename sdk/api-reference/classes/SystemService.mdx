The `SystemService` class provides health checks and basic metadata about the Tybrite API. These methods are public and do not require authentication apart from getStoreInfo.

Access this service via `client.system`.

### `getStoreInfo`

Retrieve comprehensive store metadata, configuration, and catalog statistics in a single API call. This endpoint is specifically optimized for initial data synchronizations, AI agent context setting, and dashboard overviews.

The `store` section includes business context — `name`, `logo_url`, `description`, `website`, `phone`, `email`, and `address` (any of which may be `null`) — alongside currencies, timezone, and creation date. `logo_variants` carries the same brand in the forms a storefront needs, keyed by the placement each mark is drawn for: `light_bg`, `dark_bg`, `icon`, `wordmark`, `monochrome`, and `primary`. Each entry is `{ url, usage_note }`, where `usage_note` is the merchant's own guidance for that mark or `null`. Every variant is optional and the object is empty when a merchant has supplied none, so it can be indexed without a guard — fall back to `logo_url` for any placement that is absent. Rendering `logo_url` everywhere means recolouring or shrinking one file: a full-colour lockup is unreadable at favicon size, and a dark-ink wordmark disappears on a dark header. `shopping_assistant` is the name and logo the merchant has given their shopping assistant, `{ name, logo_url }`, each `null` when not set; a storefront chat or an assistant shopping the store uses it to present the assistant the way the store does. It also carries `commerce_model`: `retail` (a normal browse → add-to-cart → pay-now storefront) or `wholesale` (the store sells to business buyers, often on payment terms). A wholesale storefront supports two buying flows — direct checkout, for an approved buyer reordering routine items, and request-for-quote, for negotiated or bespoke orders. `client.b2B.createDirectOrder` returns a `settlement` of `terms` (a terms invoice was issued, and is paid against the invoice) or `pay_now` (complete payment against the returned `order_id` through `/v1/payments/*`, exactly like a retail order). The server decides which from the buyer's own terms, so a wholesale storefront builds both flows and branches on that response rather than on `commerce_model`. A wholesale store additionally carries `vendor_type`, its position in the supply chain from upstream to downstream: `supplier` (raw materials, components, or unbranded goods sold to other producers), `manufacturer` (makes the finished product), `distributor` (an authorised reseller for a brand, usually in set regions), or `wholesaler` (buys in bulk and resells to businesses). It is `null` on a retail store. Where `commerce_model` decides how a storefront sells, `vendor_type` identifies who the seller is — buying direct from a manufacturer and buying from a wholesaler differ in price, minimum order quantity, and lead time. The `features` block also carries `returns_window_days`: how many days after delivery a shopper may start a return, or `null` when the merchant has stated no period — in which case say returns are accepted without naming a window rather than assuming a default. It is only meaningful while `returns` is true, and it is the store's policy rather than a verdict on one order; for that, call `client.returns.checkReturnEligibility`, which accounts for when the specific parcel was delivered. The window is enforced when a return is lodged, not merely advertised, so a figure shown from here is one the API will honour. The `catalog.products` block includes a thin `sample` array (at most 10 items, each `{ id, name, category, price, image, featured }`) — a small sample of products for context; use `client.products.listProducts` to browse the full catalog.

*   **Caching**: Responses are cached for 5 minutes by default. `cache: false` builds the response from the store's current data, including the `features` flags and their `feature_status`.
*   **Selective Loading**: Use the `sections` parameter to tailor the response and reduce payload size by up to 80%.
*   **Single-store only**: This endpoint describes one store. A **marketplace operator key** receives `403` — use `client.marketplace.getMarketplaceInfo` for the marketplace's own information, or `getMarketplaceInfo({ storeId })` for one merchant within it.

```typescript
// 1. Get full store configuration (all sections)
const fullInfo = await client.system.getStoreInfo();
console.log(`Connected to: ${fullInfo.store.name}`);
console.log(`Currencies supported: ${fullInfo.store.currencies.join(', ')}`);

// 2. Optimized request for AI/Agent context
const { features, catalog } = await client.system.getStoreInfo({
  sections: 'features,catalog'
});

if (features.ai_recommendations) {
  console.log(`AI enabled. Total active products: ${catalog.products.active}`);
}

// 3. Bypass cache for fresh settings
const freshData = await client.system.getStoreInfo({ cache: false });
```

#### Custom fields

A merchant can add fields of their own to their records — `fabric` on a product, `buyer_po` on an
order — and the `custom_fields` section is where you find out which ones exist before you meet a
value for one.

Reading a product does not tell you that `fabric` is the merchant's own field rather than something
the platform ships, and a field no record has filled in yet is invisible entirely. This section is
the shape of the merchant's records, so you can label and format a value correctly the first time
one appears, and offer the field in a filter or a form without waiting to discover it.

Fields are grouped by the kind of record they describe, because a field is not a store-wide fact:

```json Response
{
  "custom_fields": {
    "entities": [
      {
        "entity": "products",
        "fields": [
          { "name": "fabric", "label": "Fabric", "type": "text" },
          { "name": "country_of_origin", "label": "Country of origin", "type": "text" }
        ]
      },
      {
        "entity": "online_orders",
        "fields": [
          { "name": "priority", "label": "Priority", "type": "select", "options": ["Standard", "Express"] }
        ]
      }
    ],
    "total_fields": 3
  }
}
```

`entity` names the record the fields belong to — `products`, `product_variants`, `customers`,
`online_orders`, `returns`, `expenses` and others. `type` is one of `text`, `textarea`, `number`,
`boolean`, `select`, `multiselect`, `date`, `json`, `dimensions` or `weight`. `options` appears on a
choice field and lists the permitted values; `unit` appears on a measured field and names the unit
it is expressed in.

A merchant may keep a field private, and private is the default — a custom field often holds a cost,
a margin or an internal note. A private field does not appear here at all, not even its name, so
everything in this section is safe to show a shopper.

These are definitions. A field's **value** belongs to a record and comes back with that record, in
its own `custom_fields` array.

#### Store profile

The `profile` section is a compact form of the store profile, for a storefront that renders its
footer from the store information it already loads at startup. `contact` and `social` have the same
shape as in [`client.store.getStoreProfile`](/sdk/api-reference/classes/StoreService); `policies`
lists the published legal documents without their text; `has` reports whether each built-in
document is currently published, so footer links can be decided without a further call; and
`business` carries the legal name and the country whose law the policies are written under, or
`null` when neither is set.

#### Shipping

The `shipping` section describes how the store gets an order to a shopper, without pricing a particular
address. `delivers` is true when the store delivers anywhere, and `delivers_everywhere` when an address
outside every zone and distance rate is still delivered to — at the `everywhere_else` rate, or for
nothing when the store has set no rates at all (`configured: false`). A store that delivers everywhere
at one flat rate has an empty `zones.list` and an `everywhere_else` rate. When `everywhere_else.refuse`
is true the store delivers only inside its zones and distance rates.

Each entry in `zones.list` has a `coverage`: `area` for a zone drawn on a map, `region` for a zone
covering whole countries or postcode prefixes (listed in `countries`), and `distance` for a distance
rate. `pickup_locations` lists where an order can be collected, with each location's pickup fee and
minimum order. The price for a specific address and basket comes from
[`calculateShipping`](/sdk/api-reference/classes/ShippingService#calculateshipping).

#### Category and subcategory counts

The `catalog` section carries a `taxonomy` block listing every category and subcategory. Each entry
reports two product counts, and they answer different questions:

| Field | Counts |
| :--- | :--- |
| `product_count` | Products filed **directly** against that node. |
| `product_count_including_descendants` | Products under that node at **any depth**, including those filed against nested subcategories. |

The two differ wherever a merchant files products against subcategories rather than the category
itself: a category holding nothing directly reports `product_count: 0` while the branch beneath it
holds products, so the inclusive figure is the one to render on category navigation. It is also the
figure that matches what `GET /v1/products?category_id=…` returns, because that filter covers
descendants.

A subcategory entry additionally carries `category` and `category_id` (its parent category),
`parent_id` and `parent_name` (`null` for a top-level subcategory), and `children` — the ids of its
direct children, so a client renders breadcrumbs and the nested tree without further calls.

The `features` block is a flat set of booleans your storefront uses to show or hide capabilities: `ai_recommendations`, `semantic_search`, `multi_currency`, `dynamic_pricing`, `cms` (blog posts), `lookbooks` (shoppable lookbooks — separate from `cms`), `returns`, `gift_cards`, `promotions`, `messaging`, `specifications`, `collections`, `agentic_commerce`, and `agent_hosted_helpers`.

#### What `true` / `false` mean

Each flag answers "should I render this capability **right now**?" — not "is it permitted." A flag is `true` only when the capability is **both available to the store and has data/config to surface**. `false` is intentionally broad: it can mean the plan doesn't include the feature, the plan includes it but it isn't set up yet, or both — so a `false` flag doesn't tell you *why* it's off. Treat it as "don't render this yet."

There are two kinds of flag:

| Kind | Flags | `true` requires |
| :--- | :--- | :--- |
| **Plan-gated** | `ai_recommendations`, `semantic_search`, `multi_currency`, `dynamic_pricing`, `cms`, `lookbooks`, `returns` | The store's plan **includes** the feature **and** it's configured. By plan: **Starter** has none of these; **Growth** adds `cms`, `lookbooks`, `returns`; **Premium** / **Enterprise** add `ai_recommendations`, `semantic_search`, `dynamic_pricing`, `multi_currency`. |
| **Data-presence** (every plan) | `gift_cards`, `promotions`, `messaging`, `specifications`, `collections` | The store **has at least one** of that item (e.g. `gift_cards: true` = at least one gift card issued). Not plan-gated; `false` means none exist yet. |
| **Shopping assistants** | `agentic_commerce`, `agent_hosted_helpers` | `agentic_commerce` is `true` on every store: the [Agent API](/sdk/api-reference/classes/AgentService) is available to assistants shopping it. `agent_hosted_helpers` is `true` while the Agent API's hosted helpers (`interpret`, `draftCartFromIntent`) can be called. |

#### `feature_status` — the reason behind each flag

Because `false` is ambiguous, `features` also includes a **`feature_status`** object keyed by the same names, telling you *why*:

| Status | Meaning | What to do |
| :--- | :--- | :--- |
| `available` | Usable now (the boolean is `true`). | Render the feature. |
| `awaiting_data` | In the plan (or ungated) but no data yet (boolean `false`). | **Pre-build the UI** — it lights up automatically once the merchant adds data; no redeploy needed. |
| `not_in_plan` | A plan-gated feature the store's plan excludes (boolean `false`). | Hide it; an upgrade is required. |
| `unavailable` | Switched off or not ready at the moment (boolean `false`). The reason is not disclosed. | Hide it for now; it can return to `available` without any change on your side. `agent_hosted_helpers` is always `available` or `unavailable`. |

So a Premium store with no pricing rules yet returns `dynamic_pricing: false` **and** `feature_status.dynamic_pricing: "awaiting_data"` — you can ship the dynamic-pricing UI ahead of time and it activates when the first rule is created. Data-presence features are never `not_in_plan`.

```typescript
const { features } = await client.system.getStoreInfo({ sections: 'features' });

if (features.gift_cards) {
  renderGiftCardField();                                  // available — show it
} else if (features.feature_status.gift_cards === 'awaiting_data') {
  renderGiftCardField({ disabledUntilData: true });       // build it now; it'll activate on first card
}
// feature_status === 'not_in_plan' → don't build it (upgrade required)
```

### `healthCheck`

Verify the operational status of the Tybrite API. The gateway probes all individual services in parallel and returns a per-service status map alongside an overall rollup. Useful for monitoring integrations, connectivity troubleshooting, or building your own status dashboards.

```typescript
const health = await client.system.healthCheck();

if (health.status === 'ok') {
  console.log('All systems operational.');
} else if (health.status === 'degraded') {
  // Find which services are affected
  const affected = Object.entries(health.workers)
    .filter(([, w]) => w.status !== 'ok')
    .map(([name]) => name);
  console.warn(`Partial outage — affected services: ${affected.join(', ')}`);
} else {
  console.error('API is reporting a major outage.');
}
```

**Response shape:**

```typescript
{
  status: 'ok' | 'degraded' | 'down';  // overall rollup
  gateway: 'ok';                         // gateway is always ok if you received this response
  latency_ms: number;                    // total probe time in ms
  workers: {
    [serviceName: string]: {
      status: 'ok' | 'error';
      latency_ms: number | null;         // null when the service timed out
    };
  };
  timestamp: string;   // ISO 8601
  version: string;     // API version
}
```

**Status semantics:**

| `status` | HTTP | Meaning |
| :--- | :--- | :--- |
| `ok` | 200 | All services healthy |
| `degraded` | 207 | One or more services errored or timed out |
| `down` | — | Gateway unreachable (detected externally, not self-reported) |

Each service probe has a 3-second timeout. A service that exceeds it returns `{ status: 'error', latency_ms: null }`.

<Note>
  **Caching:** `getStoreInfo` responses are cached for **5 minutes (300s)**. Repeat calls return quickly from cache. Pass `cache: false` to force a fresh response.
</Note>

## Response Codes

### `getApiInfo` (`GET /`)

| Code | Meaning |
| :--- | :--- |
| `200` | API metadata returned. |

### `healthCheck` (`GET /v1/health`)

| Code | Meaning |
| :--- | :--- |
| `200` | All services operational. |
| `207` | Partial outage — one or more services degraded. |

Both endpoints are unauthenticated — no `401`, `403`, or `429` is emitted.

### `getStoreInfo` (`GET /v1/store/info`)

Requires authentication. Both **publishable** and **secret** keys are accepted.

| Code | Meaning |
| :--- | :--- |
| `200` | Store info returned (possibly served from cache). |
| `400` | Invalid `sections` parameter (unknown section name). |
| `401` | Invalid or missing API key. |
| `403` | Forbidden — a marketplace operator key was used (use `getMarketplaceInfo` instead), or the key is disabled / store suspended. |
| `429` | Rate limit exceeded. |
| `500` | Internal server error. |
